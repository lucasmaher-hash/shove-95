## Build Philosophy

1. **Each phase ships something usable.** No phase leaves the app broken. After any phase, you can run it on the simulator and demo what exists.
2. **Infrastructure before features.** Phase 0 sets up the project, the shared package, and the design tokens so every later task builds on a working foundation.
3. **Magic moment first, skin second.** The swipe-to-defer works (unstyled) by the end of Phase 2. The Win95 skin lands in Phase 3 on top of proven interactions — never the other way around.
4. **Logic lives in the package, tested.** Everything date- or placement-shaped goes into `Shove95Kit` as pure functions with unit tests. If a bucket bug can be caught by a test, it must be.
5. **Interaction risk gets a spike.** The known-hard piece (swipe + scroll + context menu + drag-reorder coexisting) gets a timeboxed spike task with an explicit fallback decision, before anything is built on it.
6. **Derive, don't eyeball.** Every visual value comes from `docs/design.md`. If something looks wrong, check the derivation before changing a number.
7. **Test as you go.** Each task's Notes end with a verification step. Run it before checking the box.
8. **Review before proceeding.** Push each completed phase as a PR and let a review agent (e.g. CodeRabbit) review it before the next phase. If the repo has no GitHub remote, commit locally per phase and note you're forgoing external review.

**Hard external gate:** the paid Apple Developer account ($99/yr) must exist **before Phase 5** (CloudKit does not run on a free team). Phases 0–4 run entirely on a free/personal team.

## Agent Session Guide

### How to Use This Roadmap with Your Coding Agent

1. **Start a session:** Give your coding agent the phase prompt at the beginning of each phase.
2. **Read selectively:** Each phase lists its Reference sections — the specific parts of the PRD, vision doc, and design.md needed for that phase. The agent should read only those sections, not the entire documents.
3. **Let it work:** The agent reads the roadmap, finds the first unchecked task, implements it, runs the task's Verify step, and marks it complete.
4. **One session = one phase (ideally):** If you stop mid-phase, the agent resumes from the first unchecked task.
5. **Push a PR for review:** When a phase is complete, push the branch (`phase-{N}/{slug}`) and let a review agent (e.g. [CodeRabbit](https://coderabbit.ai)) review before starting the next phase. Fix findings on the same branch; merge when clean.
6. **Need more context?** If a task references a section not in the phase's Reference list, read just that section on demand.

### Session Tips

- **Don't read everything.** Loading all five docs wastes context; the Reference sections are the map.
- **Don't skip tasks.** Ordering resolves dependencies. The spike (TASK-019) especially must precede everything built on it.
- **Founder tasks are gates.** TASK-001/002/004(download)/049/056(Pages)/062(art)/065(soak) need Lucas — the agent should stop and ask rather than fake them.
- **Verify on device for anything gestural or haptic.** The simulator lies about feel.
- **Update the status line** after each task: `**Status:** X/66 tasks complete` + current phase.
- **Two hard rules from the PRD travel with every session:** the model type is `TaskItem` (never `Task`), and nothing in `Shove95Kit` imports SwiftUI/UIKit.

### Prompt Templates

**Starting a new phase:**
> "Read docs/product-roadmap.md and find the current phase. Read only the Reference sections listed for that phase from docs/prd.md, docs/product-vision.md, and docs/design.md. Start on the first unchecked task. After completing each task, run its Verify step, then update the checkbox to [x] and the status line. Continue through the phase."

**Resuming after a break:**
> "Read docs/product-roadmap.md. Find the first unchecked task. Read only the current phase's Reference sections. Continue from there."

**After completing a phase:**
> "Phase [N] is complete. Create branch `phase-{N}/{slug}`, commit all work, push, and open a PR titled 'Phase {N}: {Title}' with the phase goal, completed task range, and what to verify manually."

**Fixing an issue:**
> "There's a problem with [description]. Read the relevant PRD section for the expected behavior and fix it. Don't mark new tasks complete until the fix is verified."
