## 1. What this is

**shove95** is an iOS to-do app with **two complete design languages**, not one
app with a theme switch:

- **Win95** — a pixel-faithful Windows 95 interface. Bevels, a 1995 palette, a
  bitmap-derived typeface, whole-pixel geometry.
- **Skeu** — soft skeuomorphism. Glass, troughs, tinted shadows, one light
  source from the top slightly left.

Both looks are first-class. Every feature exists in both, and **a reader who
flips Design must find every control where they left it.** That is the rule
that generates most of the work: build something in one look and you are half
done.

Stack: SwiftUI + SwiftData + CloudKit (private DB), iOS 26 target, plus a
Live Activity via ActivityKit.

## 3. Build, test, deploy — do this every time

**The founder's standing instruction: after every build, install to BOTH the
simulator and the connected iPhone, without being asked.** This is saved in
memory as `deploy-to-phone-and-simulator.md`. Do not skip it and do not ask.

Simulator (iPhone 17 Pro):

```bash
xcodebuild -project shove95/shove95.xcodeproj -scheme shove95 -destination 'id=E086D24D-AF41-4EA3-B0D1-552A333ECB05' -derivedDataPath /tmp/dd build
```

Then launch it with the iOS Simulator MCP tool (`control`, action `launch`,
`app_path` = `<derivedData>/Build/Products/Debug-iphonesimulator/shove95.app`,
`udid` = `E086D24D-AF41-4EA3-B0D1-552A333ECB05`).

Phone (device id and the devicectl UUID are different values — both are needed):

```bash
xcodebuild -project shove95/shove95.xcodeproj -scheme shove95 -destination 'id=00008101-001168291429001E' -derivedDataPath /tmp/dev build
```

```bash
xcrun devicectl device install app --device 38FE9E86-BCCC-53D9-ADB9-F98D0155CCF3 /tmp/dev/Build/Products/Debug-iphoneos/shove95.app
```

Tests (fast, run them before committing anything that touches logic):

```bash

```

## 5. The two design systems — the rules that get enforced

`/Users/lucasmaher/TEMP/CLAUDE.md` carries the full SkeuKit hard rules. The
ones that get violated most:

- **No hardcoded colours** outside the theme folders. Read colour via
  `@Environment(\.skeu)` in skeu, via `Win95.*` in Win95. No `Color.white`,
  `.black`, `.primary`, `.secondary`, no hex literals in a component.
- **No textures.** Depth comes from gradients, rim strokes and shadows only.
- **One light source**, top slightly left, `(-0.25, -1.0)`. Never inverted per
  component.
- **Shadows are tinted** (`skeu.shadow`, a dark brown), never black or grey,
  and always ambient + contact in a pair.
- **Radii** from `SkeuRadius`, always `style: .continuous`; nested children use
  `nestedRadius(parent, inset:)`.
- **Pick one depth** from `carved · recessed · flush · raised · floating ·
  overlay`. No in-between shadow values.
- **Theming must stay live** — any screen must re-skin by changing only
  `.skeuTheme(...)`. If it doesn't, the component is wrong.

Win95 (`docs/design.md`):

- **Nothing hardcodes a point value.** Everything multiplies the environment
  `pixel` unit (2 at default type size, 3 and 4 at accessibility sizes). Values
  are stated in 1995 pixels in `Win95.Px`.
- **Whole pixels only.** This is why the app draws its own pixel glyphs instead
  of using SF Symbols in that look — symbols sit on a continuous curve and land
  on fractional pixels at every scale step. See `PixelPencil` in
  `SettingsView.swift` for the pattern.
- Tap targets stay ≥ 44pt even where the 1995 spec would be smaller.

## 6. Traps — every one of these cost a bug report

**Read this section twice.** These are properties of SwiftUI and UIKit that the
code has already been bitten by. Several bit more than once.

1. **`offset` moves what is DRAWN, not the layout frame.** A `.background`
   attached after an `.offset` is measured against the unshifted frame and
   stays put. The skeu row slid out from under its own lit slat this way. Put
   the background *before* the offset. Same for `.scaleEffect`.

2. **A `GeometryReader` wrapping content LAYS OUT, it does not merely measure.**
   Wrapping a sheet in `GeometryReader { }.ignoresSafeArea()` pulled the header
   up under the status bar on all four screens in both looks. To measure
   without participating in layout, put the reader in a `.background`.

3. **A filled `Shape` is hittable only where the ink lands.** Circular controls
   need `.contentShape(Circle())` or taps in the corners do nothing. This is
   what made the ✕ buttons feel unreliable.

4. **A `Button` wrapping a gesture eats the gesture.** `.skeuPress` inside a
   `Button` label never fires — the Button takes the touch first. Remove the
   Button and let the press modifier own the interaction.

5. **Padding inside a fixed `.frame(height:)` is squeezed back out.** Adding
   padding above the title-bar controls did nothing; the bar's own height had
   to grow (`Win95.Px.titleBar`).

6. **Nothing is rendered behind a `fullScreenCover`.** Offsetting a sheet
   reveals black, not the screen it came from. The fix is
   `.presentationBackground(.clear)` on the cover plus a sheet that paints its
   own opaque ground. A backdrop colour that "matches what's behind" is a
   stand-in that breaks the moment anything fades it.

7. **`UIImage(data:)` inside a body decodes the JPEG on every body run**, and
   bodies run constantly. This is what made photo rows flicker mid-gesture.
   Everything goes through `PhotoCache`.

8. **Haptic generators must be held and prepared.** One built and fired in the
   same breath drops its first impulse.

9. **Static properties are invisible to SwiftUI.** `Win95.text` and friends are
   statics, so a view whose inputs haven't changed keeps painting the old
   palette. The app works around this with `.id(scheme.id)` on the root subtree
   and by reading `\.win95Scheme` / `\.appFace` from the environment purely to
   force a re-render. If you add a view that must repaint on a scheme or face
   change, read one of those.

10. **`AppSettings.init()` must assign the colour slot LAST** — its observer
    reads `scheme`, which other properties have to have set up first.

11. **`drawingGroup()` rasterises at layout bounds** and clips anything that
    bleeds outside them (glows, shadows).

12. **Scrolling to top on a data swap needs a runloop turn.** Calling `scrollTo`
    inline on the same change that re-points the store aims at the outgoing
    list. Defer it, and give the anchor a non-zero height.

## 7. Decisions already settled — do not reopen

- **Duplicate workspace names are forbidden**, not merged.
- **The skeu light source stays as drawn.**
- **Animations are wanted everywhere.** The transitions ban is gone.
- **Per-tab time toggle**: turning it off means the tab *moves nothing* — no
  rollover at midnight, no pull into Today, no overdue chip. It keeps its name
  and behaves like General does today.
- **Shared colour**: one setting, five slots, matched **by position**. Slot 1 is
  Windows Standard / Cream, slot 2 Desert / Clay, and so on. Each look draws its
  own palette for the shared slot so the two cannot drift. Silver is skeu-only,
  slot 5; picking it in skeu falls back to the last-used colour in Win95.
- **Onboarding** runs on first launch, over the empty list, with a sample task
  that is removed afterwards.
- **Name length** is capped at `AppSettings.maxNameLength` (12) and must be
  *refused*, not truncated — live via `.limited(to:)` on the binding, plus a
  load-time trim and a store-level bound.
- **The How-to screen** is visual: `HowToContent.swift` holds one source of
  content, `HowToGlyph.swift` draws the pictograms, both looks render it.
- **#18, noted but not built**: the retro look and extra colours may later sit
  behind an App Store rating. Keep the colour and face settings easy to gate.
  Do not build the gate.

## 9. Working method that has held up

1. Read the relevant existing code before editing. The files are long and the
   comments carry decisions you cannot infer.
2. Make the change in **both looks** in the same pass. The single most common
   defect in this project's history is a feature that exists in skeu and not in
   Win95, or vice versa — it has happened with photo delete, workspace delete
   and the swipe backdrop.
3. Build for the simulator, then the phone, then install to both.
4. Run `swift test --package-path Shove95Kit` if logic moved.
5. Commit with a prose message explaining the mechanism.
6. Report back plainly: what changed, why it was broken, and **what you did not
   verify**. The founder tests on the device and wants to know where to look.

Do not claim something is fixed that you have only compiled.
